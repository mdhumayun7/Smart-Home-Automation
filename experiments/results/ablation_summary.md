## 1. Command-path design ablation

Twelve designs, same adversary, same scenario, same seeds. The adversary floods
the command topic and captures the legitimate command off the wire for replay.

Availability is measured as the proportion of five operator publish attempts,
spaced 200 ms apart, that reach the state machine while the adversary floods at
the configured rate. Throughout the trial prologue the adversary floods at full
rate but cannot itself arm the system, so an observed arm is attributable to the
operator; its nuisance arming is measured separately in the replay column. A
single-command boolean was found to measure token-bucket phase rather than
availability, and is not reported: see `docs/SECURITY_ANALYSIS.md` section 9.

| Design | Trials | Operator commands admitted under flood | Defeated by capture-and-replay (attacked trials) | Attacker disarmed | Alarm fired | Invariant violations |
|---|---|---|---|---|---|---|
| No command defence | 300 | 1250/1250 | 250/250 | 0 | 300/300 | 0 |
| Token-bucket rate limit (5/s) | 300 | 737/1250 | 250/250 | 0 | 300/300 | 0 |
| Static shared token | 300 | 1250/1250 | 250/250 | 0 | 300/300 | 0 |
| TLS + broker credentials | 300 | 1250/1250 | 0/250 | 0 | 300/300 | 0 |
| TLS, credentials leaked | 300 | 1250/1250 | 250/250 | 246 | 50/300 | 250 |
| TLS + ACL, shared credential leaked | 300 | 1250/1250 | 250/250 | 246 | 50/300 | 250 |
| TLS + ACL, controller credential leaked | 300 | 1250/1250 | 250/250 | 246 | 50/300 | 250 |
| TLS + ACL, device credential leaked | 300 | 1250/1250 | 0/250 | 0 | 300/300 | 0 |
| HMAC-SHA256 + counter | 300 | 1250/1250 | 0/250 | 0 | 300/300 | 0 |
| HMAC, command key leaked | 300 | 0/1250 | 245/250 | 234 | 50/300 | 250 |
| TLS + ACL + HMAC, device flash dumped | 300 | 1250/1250 | 0/250 | 0 | 300/300 | 0 |
| TLS + ACL + HMAC, controller compromised (credential + key) | 300 | 0/1250 | 245/250 | 234 | 50/300 | 250 |

Safety latency was identical across all twelve designs (median 151 ms, standard deviation 0.0 ms), which is
expected: the harness advances a logical clock, so there is no contention to
measure. This says nothing about physical timing.

**Reading.** Availability, integrity and the safety function are separable,
and most of the eleven designs fail at least one of them:

- A **rate limit** cannot tell a legitimate command from a flood, so it drops
  the operator's command along with the attacker's, and it leaves integrity
  completely untouched. Its effect on availability is not monotonic in attack
  intensity: a moderate flood (10-100 commands/s) costs the operator most or
  all of its attempts, while an extreme flood costs it none, because arrivals
  that find the
  bucket below the admission threshold are rejected *without consuming a
  token*, which pins the bucket just under that threshold and leaves enough
  refill for the next arrival. This is a property of the limiter, measured
  rather than assumed; see docs/SECURITY_ANALYSIS.md section 9.
- A **static token** restores availability, because the edge filters the flood
  cheaply. It is still defeated the moment the attacker captures one
  legitimate command, since the token travels in plaintext.
- Only the **MAC plus monotonic counter** provides both. The counter, not the
  MAC, is what defeats replay; a MAC alone would behave like the token row.

### 1.2 Statistical comparison

The two transport arms are built from identical source with identical flags
and run on identical seeds; the adversary's possession of a valid broker
credential is the only variable that differs.

**The arms share one seed set, so the design is matched pairs, and the
paired test below is the primary one.** Every arm is run on the same 300
seeds with the same seed-to-attack-rate mapping, so each seed gives a
matched pair and only discordant pairs carry information. The Fisher
figures that follow assume two independent samples, which this design
does not provide; they are reported as a labelled sensitivity analysis
only. Treating matched arms as independent overstated the evidence by
many orders of magnitude in an earlier version of this document.

- Alarm activation, credentials leaked: 50/300 (16.7 %, 95 % Wilson CI [12.9 %, 21.3 %]).
- Alarm activation, credentials held: 300/300 (100.0 %).
- **Primary test (paired, McNemar exact, one-sided):** 300 matched pairs, 250 discordant (250 lost the alarm when the credential leaked, 0 gained it), p = 5.527e-76.
- Secondary, *assumes independence this design does not have*: Fisher exact one-sided p = 9.827e-119.

- Operator availability, rate limit 737/1250 (59.0 %) against HMAC 1250/1250 (100.0 %).
- **Clustering.** The 5 attempts in a trial share its bucket phase: 231/250 rate-limiter trials admitted either all 5 or none. ICC = 0.669, design effect 3.68, so the effective sample size is about 340, not 1250.
- **Primary test (paired by seed at the trial level, McNemar exact, one-sided):** 112 discordant pairs, p = 1.926e-34.
- Secondary, *treats 1250 clustered attempts as independent and ignores the pairing*: Fisher exact one-sided p = 3.531e-184. The conclusion is unchanged; the precision is not.

### 1.3 What each control protects, by which secret the adversary holds

Broker-side access control and application-layer authentication fail under
*different* compromises, so neither dominates the other. The table reads
down the adversary's capability, not down a ranking of mechanisms.

| Controls in place | Secret the adversary holds | Unauthorised disarm | Alarm fired | Operator locked out |
|---|---|---|---|---|
| TLS, no ACL | none | **no** | 300/300 | no (1250/1250 admitted) |
| TLS, no ACL | any broker credential | **yes** | 50/300 | no (1250/1250 admitted) |
| TLS + per-client ACL | the one shared credential | **yes** | 50/300 | no (1250/1250 admitted) |
| TLS + per-client ACL | controller credential | **yes** | 50/300 | no (1250/1250 admitted) |
| TLS + per-client ACL | device credential | **no** | 300/300 | no (1250/1250 admitted) |
| HMAC + counter | any broker credential | **no** | 300/300 | no (1250/1250 admitted) |
| HMAC + counter | controller credential and command key | **yes** | 50/300 | **yes** (0/1250 admitted) |
| TLS + ACL + HMAC | device credential and command key (flash dump) | **no** | 300/300 | no (1250/1250 admitted) |
| TLS + ACL + HMAC | controller credential and command key | **yes** | 50/300 | **yes** (0/1250 admitted) |

Four readings follow, and the last three cut against this project's own
mechanism:

- A per-client ACL is **not** a weaker substitute for application-layer
  authentication. It contains a *device* compromise completely, which
  matters for an embedded product because the device is the physically
  accessible component and its broker credentials sit in a readable flash
  image. It does nothing against a compromised controller, because that
  identity is the one the ACL must authorise to publish commands.
- A shared credential defeats the ACL entirely. The ACL must grant the
  single identity write access to the command topic for the system to
  work, so the configuration collapses to the no-ACL case. Credential
  separation, not the ACL syntax, is what carries the protection.
- **A MAC does not survive key compromise, and the key is in the same
  flash image.** With the command key dumped, the signed path is defeated
  exactly as the unsigned one is. Only the combination holds: with both an
  ACL and a MAC, an adversary who dumps the device gets a key it can sign
  with and a credential the broker will not let it publish commands under.
  The defence that survives in this table is layered, not cryptographic.
- **The layered configuration does not survive every compromise, and an
  earlier draft of this document said it did.** It survives every
  single-secret compromise and it survives a device flash dump, because
  the ACL refuses the device identity permission to publish commands. It
  does *not* survive a compromised controller host, which yields both a
  credential the ACL must permit to publish and the shared key needed to
  sign: neither layer refuses, and the adversary disarms. Layering raises
  the cost of an attack; it does not close the set.
- **Under key compromise the replay counter becomes a lockout against the
  owner.** This was not anticipated and was found in the data. Counters are
  not secret, so an adversary holding the key can sign commands with a
  counter far above the operator's; the device persists it, and every
  subsequent operator command is then rejected as a replay. In this arm the
  operator is admitted in 0 of 1250 attempts across all attacked trials. A
  monotonic counter defeats replay and, under key compromise, denies
  service to the legitimate user at the same time. Recovery needs a key
  change and a counter reset, neither of which this firmware supports
  remotely.

## 2. Deauthentication detector parameter sensitivity

traffic, over ten simulated minutes per run. **The benign arrival model is an
assumption, not a measurement**: no capture of real management traffic was
available, so these characterise the detector's logic, not any real network.

**This sweep changed the firmware.** The original threshold of 8 fired
spuriously in 79.8% of benign ten-minute runs at 60
frames/min, which is an ordinary busy multi-AP environment. The default is
now **12**, which fires in 0.25% of the same runs while
still detecting every swept attack rate with no misses. The cost is about
214 ms of extra detection latency at 20 frames/s.
